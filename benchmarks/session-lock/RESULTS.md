# Session lock: Rust vs ckb-js-vm

Generated by `npm run bench:session-lock` against the ckb-session-kit lock at
commit 49227cd (rules and error codes 10-20). Both implementations
run the same 58 scenarios in the real CKB-VM (ckb-testtool + ckb-debugger) and
**agree on every accept/reject decision**.
The scenarios cover plain CKB sessions (38) and token sessions (20); the
token is a stand-in type script, since the lock only compares its type hash and
reads the amount from the cell data.

This compares these two implementations of one lock only; it is not a verdict
on Rust against JavaScript scripts in general.
The Rust lock is `cargo build --release` of `contracts/session-lock` at that
commit, with its `[profile.release]`: `opt-level = "s"`, `lto = true`,
`codegen-units = 1`, `panic = "abort"`, `overflow-checks = true`,
`strip = true`; target `riscv64imac-unknown-none-elf` with
`-C target-feature=+zba,+zbb,+zbc,+zbs,-a` (its `.cargo/config.toml`);
ckb-std 1.1.0 (its `Cargo.lock`). The repository pins no Rust toolchain, so
CI builds with the runner's stable rustc.

| | Rust | ckb-js-vm |
|---|---:|---:|
| Code deployed | 7,656 B binary | 30,917 B bytecode + 410,248 B VM |
| Mean cycles, accepted plain CKB spends | 14,758 | 15,037,968 |
| Mean cycles, accepted token spends | 20,348 | 15,518,698 |
| Median ratio, all scenarios | 1× | 1009× |
| Cheapest run (bad args: start-up cost) | 3,145 | 14,272,805 |

**Where the ckb-js-vm cycles go.** The cheapest run — args rejected almost
immediately — still costs 14,272,805 cycles: the price of starting the
JavaScript VM, loading the bytecode and running the bundle's top-level code,
most of it @ckb-js-std/core initialising (broken down in "Startup floor vs
bytecode size" below). An accepted plain CKB spend averages
15,037,968, so the lock's own logic is only about 765,163 of it
(5%). For a script this small, ckb-js-vm's cost is almost
entirely fixed start-up, and the logic itself runs at roughly
66× the Rust logic's cycles.

## Compared with the 8 Oct version

The 8 Oct run measured session-kit 3745aa0, before the lock gained no
splitting (16), the key-cell rule (17), no type scripts (18) and token sessions
(19, 20). Its 20 scenarios are the first 20 below, unchanged, so this is the
same transactions against both versions:

| Same 20 scenarios | Rust, 8 Oct | Rust, now | ckb-js-vm, 8 Oct | ckb-js-vm, now |
|---|---:|---:|---:|---:|
| Code deployed | 4,344 B | 7,656 B | 29,118 B | 30,917 B |
| Mean cycles, accepted spends | 12,263 | 15,393 (+26%) | 14,573,318 | 15,074,377 (+3%) |
| Cheapest run (start-up cost) | 2,318 | 3,145 | 13,916,789 | 14,273,079 |
| Median ratio | | | 2027× | 1609× |

For ckb-js-vm, most of the increase is start-up: the 8 Oct TypeScript port,
rebuilt with today's toolchain, still costs exactly its 8 Oct cycles, so the
extra 356,290 cycles before any logic runs come from the new version's
start-up: mostly its new top-level `2n ** 128n - 1n` constant, the rest the
larger bytecode (see "Startup floor vs bytecode size" below). The Rust lock grew
more in relative terms (a larger binary to load, and the extra checks on every
output), which is why the ratio fell.

## Startup floor vs bytecode size

Generated by `node benchmarks/session-lock/floor.mjs`. Every script here exits as
soon as it runs, in the same transaction as "args too short" above, under the
same ckb-js-vm (the one ckb-testtool 1.0.5 ships, 410,248 B, sha256
`721318de24bff4d8…`) and ckb-debugger 1.1.1. CKB-VM is deterministic, so each
number is one run.

| Script, exiting at once | Bytecode | Cycles |
|---|---:|---:|
| ckb-js-vm `-h`: ELF loaded, no JS engine | – | 119,197 |
| ckb-js-vm `-e ""`: engine up, empty script, no code cell | 0 B | 3,574,319 |
| `exit(10)` | 86 B | 3,565,998 |
| `throw new Error()` | 49 B | 3,589,571 |
| empty module | 34 B | 3,560,452 |
| `exit(10)` + ~1 KB of never-called code | 949 B | 3,637,226 |
| `exit(10)` + ~10 KB of never-called code | 10,198 B | 4,261,788 |
| `exit(10)` + ~30 KB of never-called code | 31,337 B | 5,677,552 |
| `exit(10)` + ~50 KB of never-called code | 53,009 B | 7,052,302 |
| `exit(10)` + ~100 KB of never-called code | 108,067 B | 10,517,722 |
| `exit(10)` + `import { HighLevel } from "@ckb-js-std/core"` | 27,928 B | 12,642,100 |
| **session lock, bad args** (as compare.mjs builds it) | 30,917 B | 14,273,079 |
| session lock, not minified | 35,058 B | 15,429,215 |
| session lock, `U128_MAX` as a hex literal | 30,919 B | 14,029,181 |
| session lock, both BigInt limits as hex literals | 30,913 B | 13,179,933 |
| the lock's bad-args check on the raw bindings, no library | 233 B | 3,595,171 |
| `exit(10)` as JS source in the code cell | 55 B source | 3,608,081 |
| session lock as JS source in the code cell | 24,503 B source | 46,694,645 |

**Bytecode size alone is cheap.** Dead code costs about 64 cycles per byte
of bytecode to load (never run): 100 KB adds 6,951,724. At the lock's size that is
about 1,990,410. A tiny script that exits at once costs
3,560,452 to 3,589,571 however it exits: that is the real floor of ckb-js-vm here.

**What the lock's 14,273,079 is made of.** The same rejection, with
`bindings.currentCycles()` markers added in memory (they add 53,606 cycles;
js/index.ts is unchanged):

| Stage | Cycles | Share |
|---|---:|---:|
| ckb-js-vm starts QuickJS and reaches the first statement of a 149-byte script | 3,571,428 | 25% |
| reading the lock's 30,917 B of bytecode and setting up the module | 2,735,286 | 19% |
| @ckb-js-std/core's top-level code (building its molecule codecs) | 6,556,370 | 46% |
| the lock's own top-level code: `2n ** 64n - 1n` and `2n ** 128n - 1n` | 1,097,798 | 8% |
| `HighLevel.loadScript()`, decoding the script | 334,281 | 2% |
| the args-length check and the exit | 31,522 | 0% |
| **total** | **14,326,685** | |

Inside @ckb-js-std/core, the modules whose top-level code costs most (a marker
after every module, about 7,500 cycles each included):
`num/index.js` 1,058,780, `molecule/predefined.js` 1,696,211, `ckb/blockchain.js` 606,282, `ckb/script.js` 345,699, `ckb/transaction.js` 1,651,345, `high-level/high-level.js` 1,114,619; the other 11 modules
190,258 together.

So for this lock about a quarter of the floor is ckb-js-vm itself, a fifth is
loading the bytecode, and over half is JavaScript that runs before `main()`:
the library's module initialisation and two BigInt constants. Without the
library, the same args check exits at 3,595,171. Writing the two limits
as hex literals saves 1,093,146. The 128-bit one, added with token sessions,
alone costs 243,898: that, not the larger bytecode, is most of the
356,290 start-up increase since 8 Oct noted above (the
1,799 extra bytes account for about 115,818).
Reading the lock's bytecode (2,735,286) also costs more than the same size of dead code;
the difference is most likely module setup, such as linking imports and creating
the top-level functions.
Shipping JS source instead of bytecode costs 46,694,645: compiling on chain is
far more expensive than reading bytecode.

ckb-debugger's flamegraph cannot split this further: the ckb-js-vm binary is
stripped, so the whole run is one frame.
